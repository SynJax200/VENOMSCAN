1. Executive summary

The client review evaluated a PDF, not the implementation. This audit is the missing code-level layer. It separates three questions that the review correctly treated as one:

  • Does the capability exist in code? For several challenged areas, yes, and it has dedicated tests.
  • Was the capability actually exercised and proven in the reviewed report? For AI, endpoint verification, IDOR/function authorization and API probing, no.
  • Does the report communicate what really happened? No in four material places: unverified endpoint candidates are counted as inventory, skipped checks appear as completed, observed headers are omitted, and fallback text is headed “AI analyst note”.

1.1 What Sir got right

  1. AI is not demonstrated. The report calls deterministic text an “AI analyst note”. The database records all four analyses as provider=fallback, model=deterministic. The running API currently reports provider_configured=False. Sir is right about the delivered result; the nuance is that provider adapters, grounding, retrieval, caching and fallback logic exist and are tested.
  2. Endpoint intelligence is noisy. The scan stored 73 endpoints; 38 came from JavaScript. The inventory includes ${this.canonicalString()}, ${e.key.getCollectionPath().canonicalString()}, /_next, /_app, /_document, /_error, /_next/image and bundled JavaScript chunks. Endpoint verification probed 20 and received 20 × 404. Every persisted JS candidate that was not probed remains in the inventory as “unverified”.
  3. API security is mostly scaffold. The reviewed target exposed no OpenAPI document, no GraphQL endpoint and no JWT samples. GraphQL probing is hardcoded to zero. BOLA appears only as a manual candidate matrix. This is not an API security assessment engine yet.
  4. Evidence does not appear in the PDF. The engine captured the full observed response, including headers, status and body excerpt. The PDF printed only the request object. This is a rendering defect, not a collection defect.
  5. Student learning is absent from the PDF. It exists in the application (curriculum, walkthroughs, exercises, progress, API and UI) and does not exist in any report renderer.

1.2 What the PDF also hides

  • Skipped is not “no finding”. The checks table says IDOR and function-level authorization produced “no finding”, while scan events say both were skipped because no usable test accounts were configured. The target also exhausted its 120-request budget; the DOM XSS probe aborted. Those outcomes are not shown in the checks table.
  • “Live” includes 404 responses. The report says “41 live”. Six probe 404 results, one robots.txt 404 and six bundled .js files with HTTP 200 are counted as live because any non-null status is treated as live. A 404 is a fetched response, not an endpoint that exists.
  • Only one low finding is plausible on this target, but coverage is incomplete. The target already sends CSP, HSTS, X-Content-Type-Options, Referrer-Policy, Permissions-Policy and X-Frame-Options; only COOP was missing. That explains the single hardening finding. It does not excuse the skipped and budget-aborted checks being presented as completed.
Artifact validity. The reviewed 21-page report is the current active-profile output (scan started 16 Nov 2026 18:23 UTC). A later safe-profile 19-page report is not evidence that these defects were fixed: the safe profile exercises less JavaScript and fewer checks. The defects below are present in the same code path used to produce the reviewed artifact.

3. The client’s five concerns, adjudicated

A. “AI was not actually implemented” — partially valid

Delivered behavior: valid criticism. The reviewed report contains no LLM output. All four analyses were produced by the deterministic fallback. The finding note is rendered under the heading “AI analyst note” without a provenance label.

Code reality: the AI subsystem is present and tested: provider adapters for OpenAI-compatible endpoints, Anthropic and Ollama; schema-constrained completion; a grounding validator that rejects invented URLs, CVEs and references; context retrieval; prompt versioning; analysis cache; deterministic fallback for every analysis kind; and an assistant path that refuses out-of-scope targets. Relevant files: engine/venomscan_engine/ai/provider.py, ai/grounding.py, ai/features.py, ai/fallback.py, apps/api/venomscan_api/services/ai_service.py. Tests: tests/unit/ai/test_ai_engine.py, test_ai_context.py, tests/unit/api/test_ai_api.py.

Classification: Class 2 — partially implemented / not reliably verified. The engine is implemented; the live capability is not configured or proven. Calling fallback output “AI” is a reporting defect and must stop.

B. Endpoint intelligence noise — valid

This is a genuine defect with a direct code cause, not merely a display problem.

  • crawl/js.py:29-36 removes every ${...} expression before testing for regex noise. A JavaScript template such as ${this.canonicalString()} therefore becomes an empty string, passes the filter and is normalized into a route.
  • crawl/js.py:12-18 blocks images, CSS and fonts but not .js or .mjs. Bundled Next.js chunks with HTTP 200 are stored as endpoints.
  • There is no framework-path classification. /_next, /_app, /_document, /_error, /_not-found and asset namespaces all pass through.
  • intel/endpoints.py:26-30 then treats ${...} as an identifier and collapses unrelated expressions into /{id}, inventing parameters named this and e.
  • There is no rejection ledger. A candidate that is probed and returns 404 remains in the inventory as “unverified” rather than “rejected”.

Evidence: 38 JS endpoints; the list includes all framework paths above; 20 probes produced 20 × 404; 32 candidates remain unverified; the report still prints “Attack surface (73 endpoints)”.

Classification: Class 3 for framework-aware classification and candidate rejection; Class 2 for the extraction pipeline as a whole.

C. API security is mostly scaffold — valid for this target and for the engine

The target exposed no API specification and no GraphQL endpoint. The engine’s behavior at this boundary is weaker than the label suggests:

  • OpenAPI/Swagger documents are discovered on common paths and summarized when present. On this target: 0 documents, 0 routes, 0 operations.
  • JWT hygiene is offline analysis of observed tokens. No tokens were observed.
  • GraphQL candidate discovery exists, but the result is explicitly initialized with "probed": 0, "confirmed": [] in intel/api.py:179-199. Safe introspection is not implemented.
  • BOLA is a candidate matrix for manual review; the report itself calls it “non-destructive scaffold; no requests performed” (renderers.py API inventory section).
  • IDOR and function-level authorization are real checks with nine unit tests, but they did not execute in the reviewed scan.

Classification: Class 2 — partial; the active GraphQL and BOLA verification pieces are Class 3 — not implemented.

D. Vulnerability evidence is weak — partially valid, with a precise reason

The evidence collector is not the weak point. The finding in the database contains a complete observed response: URL, status 200, elapsed time, size, redirect chain, body excerpt and the full header map. The COOP absence is proven from that map.

The PDF renderer is the weak point: renderers.py:1033 and renderers.py:1129-1135 select finding.request_evidence or finding.response_evidence. Because a request object exists, the response object is never printed. The reader sees only the method and URL, exactly as Sir observed.

The impact text is specific about the attack class (“cross-origin documents can keep a window opener reference, enabling XS-Leak and Spectre-style cross-origin attacks”) but does not state the precondition or the business consequence. A better wording is: “An attacker-controlled cross-origin page opened by a signed-in user can retain a window reference to the portal and probe cross-origin state or timing, potentially disclosing authentication state or accessible resources. This check proves the header is absent; it does not prove exploitability.”

Additional reporting defect: skipped and aborted checks are indistinguishable from completed checks. apps/api/venomscan_api/services/reports.py:83-96 assigns only two results, "finding" or "no finding", based on whether a finding exists. Scan events show IDOR and function authorization were skipped and DOM XSS aborted on budget. The checks table still reports them as completed with no finding.

Classification: Class 2 — evidence capture is implemented; evidence presentation and coverage accounting are not reliable.

E. Student learning is absent from the report — valid for the PDF

The capability exists in the product: curriculum tracks, per-check learning copy, finding walkthroughs, deterministic exercises, progress tracking, API endpoints and a learning UI (apps/web/app/(app)/learning/page.tsx, apps/api/venomscan_api/routers/learning.py, engine/venomscan_engine/learning/). It is covered by engine and API tests. No report renderer references learning; the PDF contains no learning section.

Classification: Class 1 as an application capability; Class 3 as a report deliverable.

4. The three explicit classifications

Definition used here. “Implemented and tested” means code exists and passes the repository’s unit tests. It does not mean field-proven. “Partially implemented / not reliably verified” means the code exists but the delivered artifact did not exercise it, its output is incomplete, or the result is gated by configuration or credentials. “Not implemented” means no functioning code path for the capability was found.

6. Recommended sequence (no dashboard work first)

This sequence follows the client’s instruction: audit first, then close integrity gaps before adding features. It also avoids re-scanning the target until the fixes are tested on controlled applications.

Gate 0 — Truthful reporting, no new target traffic

  • Relabel all fallback output; show provider status on the report cover and every finding note (D6).
  • Add skipped/failed per-check outcomes and a coverage-limitations block (D4).
  • Render response evidence and observed headers (D3).
  • Acceptance: a keyless scan cannot present fallback as AI; no skipped check appears as “no finding”; every finding shows observed status and headers.

Phase 1 — Endpoint integrity

  • Fix JS candidate validation, asset filtering and framework namespace filtering (D1).
  • Introduce the verification ledger and correct live/not-found semantics (D2).
  • Add a controlled Next.js fixture that reproduces the reviewed noise and proves rejection.
  • Acceptance: on the fixture, the inventory contains no ${...}, no /_next family, no bundles, no 404 in “live”; every persisted JS route has a status and a reason.

Phase 2 — Authorization and API verification

  • Fix and preflight test-account decryption; make authz execution visible (D5).
  • Implement GraphQL safe probing and replace hardcoded zeros (D7).
  • Keep BOLA as a manual workflow until a safe cross-account verification design is approved; label it accordingly.
  • Acceptance: two valid accounts produce executed IDOR/function checks with evidence; GraphQL fixture produces confirmed/negative outcomes; no cross-tenant request without explicit consent.

Phase 3 — Student learning in the deliverable

  • Add the report learning section and exercises (D8).
  • Acceptance: the PDF teaches the top findings with grounded, deterministic exercises and verification steps.

Phase 4 — Dashboard and presentation enhancement

Only after the above. The client explicitly asked not to start here.

7. What this audit does not claim

  • It does not claim the reviewed target is free of vulnerabilities. A single low finding is consistent with its observed security headers, but several checks were skipped or aborted.
  • It does not claim the active probe checks are effective against real applications because unit tests passed. Efficacy requires controlled integration targets.
  • It does not claim the AI engine produces useful analysis in production; no live provider was configured in the reviewed artifact or the currently running API.
  • It does not claim the 19-page safe report supersedes the 21-page active report. The safe profile is not a fix for active-profile defects.
  • It does not include credential material, decrypted headers, API keys or target response bodies beyond the evidence already present in the reviewed scan.
